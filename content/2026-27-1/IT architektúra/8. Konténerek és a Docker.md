## 1. A Virtualizáció Alapjai

A modern IT infrastruktúrában ritkán futtatunk egyetlen operációs rendszert közvetlenül a fizikai szerver hardverén (CPU, RAM, háttértár). Az erőforrások jobb kihasználása érdekében virtualizációt használunk.

> [!definition] Hypervisor
> A hypervisor (vagy virtuális gép monitor) az a szoftveres réteg, amely elosztja és felügyeli a fizikai hardver erőforrásait az elkülönített virtuális gépek (VM) között.

### Hypervisor típusok

| Jellemző | Type 1 (Bare Metal) | Type 2 (Hosted) |
| :--- | :--- | :--- |
| **Telepítés helye** | Közvetlenül a fizikai hardverre települ. | Egy meglévő Host operációs rendszerre települ szoftverként. |
| **Teljesítmény** | Magasabb (nincs köztes OS réteg). | Alacsonyabb (a gazda OS is fogyaszt erőforrást). |
| **Példák** | Microsoft Hyper-V, VMware ESXi, KVM | VMware Workstation, Oracle VirtualBox, VMware Fusion |
| **Felhasználás** | Szerverkörnyezetek, adatközpontok, felhő. | Asztali gépek, fejlesztői tesztkörnyezetek. |

> [!warning] Fontos megjegyzés
> A Microsoft Hyper-V egy **Type 1** hypervisor, hiába egy Windows operációs rendszer felületéről kapcsoljuk be!

### Windows Subsystem for Linux (WSL 2)

A WSL 2 lehetővé teszi egy valódi Linux kernel futtatását a Windows rendszer mellett, mint egy "könnyű" virtuális gép. 
* Különösen előnyös fejlesztőknek, Windows Home alatt is fut.
* Nem a hagyományos Hyper-V Managerből kezeljük.

> [!example] WSL 2 használata Windows alatt
> ```powershell
> wsl --install -d Debian
> wsl --list --verbose
> wsl -d Debian
> ```

## 2. Virtuális Gépek vs. Konténerek

A klasszikus virtuális gépeknél (VM) **minden egyes gép saját "vendég" (Guest) operációs rendszert futtat**. Ez rengeteg tárhelyet, memóriát és karbantartást (pl. külön frissítéseket) igényel.

Ezzel szemben a konténerek megoldást nyújtanak a *"Nálam működik!"* típusú fejlesztői problémákra (amikor a függőségek vagy verziók eltérnek a különböző gépeken).

> [!definition] Konténer (Container)
> A konténer egy alkalmazást és annak futtatásához szükséges összes függőséget magában foglaló, izolált környezet, amely **megosztva használja a gazdagép (Host) operációs rendszerének kernelét**.

### Rendszerek összehasonlítása

| Szempont | Virtuális gép (VM) | Konténer |
| :--- | :--- | :--- |
| **Operációs rendszer** | Minden VM saját Guest OS-t futtat. | Közös Host kernelt használnak. |
| **Erőforrásigény** | Magas (RAM, CPU, tárhely a teljes OS miatt). | Kicsi (csak az alkalmazás és függőségei futnak). |
| **Izoláció** | Nagyon erős (teljes hardverszintű elkülönülés). | Gyengébb, folyamat-szintű izoláció. |
| **Indítási idő** | Percek (az OS-nek be kell bootolnia). | Másodpercek (csak egy folyamat indul el). |

> [!done] 💡 Érthető magyarázat (VM vs. Konténer analógia)
> Képzeld el, hogy a szervered egy nagy telek.
> A **Virtuális gép (VM)** olyan, mintha különálló családi házakat építenél a telekre. Mindegyik háznak saját alapozása, saját vízvezetéke és fűtésrendszere (Guest OS) van. Nagyon biztonságosak, de sok helyet és anyagot emésztenek fel.
> A **Konténer** olyan, mint egy modern társasház. Egy közös, vastag alapra és közös közművekre (Host Kernel) épül az összes lakás. Mindenkinek megvan a maga privát tere (izoláció), a lakások építése és fenntartása sokkal gyorsabb és olcsóbb, de a közös rendszereken osztoznak.

> [!tip] Jótanács a választáshoz
> A konténer nem vált ki minden VM-et; más feladatot optimalizál. Tipikusan **egy konténer = egy fő szolgáltatás** (pl. egy webszerver, egy adatbázis). Eltérő OS alapokhoz továbbra is VM kell.

## 3. Technikai Háttér: Hogyan izolál a Linux?

A konténerizáció a Linux kernel két alapvető szolgáltatására épül:

1. **Namespaces (Névterek):** Azt szabályozza, hogy *mit láthat* a konténer.
   * Elkülönített folyamatok (PID).
   * Saját hálózati nézet (IP, portok).
   * Saját fájlrendszer.
2. **Cgroups (Control Groups):** Azt szabályozza, hogy *mennyit használhat* a konténer.
   * Erőforrás-korlátok meghatározása.
   * Pl. maximális CPU magok száma, felhasználható RAM (pl. max $512\text{ MB}$).

## 4. A Docker Ökoszisztéma és Alapfogalmak

A piacon több konténermotor is létezik (Podman, LXC/Incus), de az iparági standard a Docker.

### A három fő alkotóelem:

1. **Image (Képfájl):**
   * Változatként azonosítható (pl. `nginx:stable`).
   * Tartalmazza az alkalmazást, a runtime-ot és a függőségeket.
   * Rétegekből (layers) áll, a nem változó rétegek újrahasznosíthatók a gyorsabb buildelés érdekében.
2. **Container (Konténer):**
   * Egy Image futó, élő példánya.
   * Saját állapotot és folyamatokat tartalmaz.
3. **Registry (Tároló):**
   * Itt osztják meg és tárolják az image-eket (pl. **Docker Hub**, Azure Container Registry).
   * Hivatkozás: `repository:tag` formátumban.

> [!done] 💡 Érthető magyarázat (Image vs. Container)
> Az **Image** egy sütemény receptje, amely pontosan leírja, miből mennyi kell, és hogyan kell megsütni. A **Konténer** maga a már megsütött, asztalon lévő sütemény. A receptből (Image) bármikor süthetsz több tucat egyforma süteményt (Konténer). A **Registry** pedig a szakácskönyv, ahonnan a receptet letöltötted.

> [!cite] Az építés és futtatás elve
> "Registryből image-et szerzünk; image-ből konténert indítunk."

## 5. Docker CLI - Alapparancsok és Életciklus

A Docker parancssoros felülete (CLI) küld kéréseket a háttérben futó **Docker Daemon**-nak, ami elvégzi a tényleges munkát.

### Image kezelése
```bash
docker pull nginx:stable         # Image letöltése a Registry-ből
docker image ls                  # Helyi image-ek listázása
docker image inspect nginx       # Részletes metaadatok lekérése
docker image rm nginx:stable     # Helyi image törlése
```

### Konténer indítása (`docker run`)
A `docker run` valójában két lépést (Létrehozás/CREATE és Indítás/START) végez el egyben.

```bash
docker run -d --name web -p 8080:80 nginx:stable
```
* `-d`: Háttérben futtatás (detached).
* `--name web`: Saját elnevezés adása a konténernek.
* `-p 8080:80`: **Port mapping.** A fizikai gazdagép $8080$-as portjára érkező kéréseket átirányítja a konténer belső $80$-as portjára ($8080 \rightarrow 80$).
* `nginx:stable`: A kiinduló image neve és a verziót jelző *tag*.

### Megfigyelés és adminisztráció
```bash
docker ps                 # Csak a futó konténerek listázása
docker ps -a              # Minden (leállított is) konténer listázása
docker stop web           # Konténer leállítása
docker start web          # Egy már létező, de leállított konténer indítása
docker rm -f web          # Konténer törlése (a -f kényszeríti, ha még fut)
docker logs web           # Az alkalmazás konzolos kimenetének megtekintése
docker exec -it web sh    # Parancssor (shell) nyitása a futó konténer belsejében
```

> [!warning] Törlési különbségek
> A konténer törlése (`docker rm`) és az image törlése (`docker image rm`) két teljesen különböző művelet! Egy image nem törölhető, amíg létezik belőle (akár leállított) konténer.

## 6. Saját Image építése: A Dockerfile

A Dockerfile az image receptje, egy szöveges fájl, amiből a Docker felépíti az image rétegeit.
Alapértelmezett fájlneve pontosan `Dockerfile` (kiterjesztés nélkül).

> [!example] Egy Python API Dockerfile példája
> ```dockerfile
> FROM python:3.12-slim
> WORKDIR /app
> COPY requirements.txt .
> RUN pip install --no-cache-dir -r requirements.txt
> COPY app.py .
> EXPOSE 8000
> CMD ["python", "app.py"]
> ```

### Fő utasítások értelmezése
* `FROM`: Megadja a kiinduló alap image-et.
* `WORKDIR`: Kijelöli a munkakönyvtárat a konténeren belül.
* `COPY`: Fájlokat másol a gazdagépről (Host) az image-be.
* `RUN`: Parancsokat futtat **az image építése (build) közben** (pl. csomagtelepítés).
* `EXPOSE`: Dokumentációs célt szolgál; jelzi, melyik porton hallgat az app. *Önmagában nem nyitja meg a portot a külvilág felé!*
* `CMD`: Az alapértelmezett indítási parancs **a konténer futtatásakor**. 
* `ENTRYPOINT`: A fő végrehajtható program, gyakran a `CMD`-vel együtt használva.

> [!danger] RUN vs. CMD - Sose keverd őket!
> A `RUN` **Build-időben** fut le, eredménye beleég az image egyik rétegeként. A `CMD` **Futásidőben** (amikor kiadod a `docker run` parancsot) hajtódik végre, és meghatározza, mit csináljon a feléledő konténer.

### Buildelés
```bash
docker build -t project-report:1.0 .
```
*(A parancs végén a pont `.` jelöli a "build context"-et, azaz az aktuális mappát, ahol a Dockerfile található).*

## 7. Tartós adatok kezelése

Mivel a konténerek írható rétege átmeneti (a konténer törlésével elvész), külső tárolót kell biztosítanunk.

1. **Volume (Kötet):** A Docker által menedzselt tároló, a konténer törlése után is megmarad.
   ```bash
   docker volume create appdata
   docker run -v appdata:/data alpine:3.20
   ```
2. **Bind Mount:** A gazdagép egy konkrét mappáját csatoljuk be a konténerbe (inkább lokális fejlesztéshez jó).

## 8. Több konténer orkesztrálása: Docker Compose

Gyakran egy projekt (pl. webalkalmazás) több konténerből áll (Frontend, API, Adatbázis). Ezeket egyben a `compose.yaml` fájl segítségével kezeljük, amely egy közös hálózatra fűzi őket, így név alapján látják egymást.

> [!example] compose.yaml példa
> ```yaml
> services:
>   web:
>     image: nginx:stable
>     ports:
>       - "8080:80"
>     depends_on:
>       - db
>   db:
>     image: postgres:17
>     environment:
>       POSTGRES_PASSWORD: demo_only
>     volumes:
>       - dbdata:/var/lib/postgresql/data
> 
> volumes:
>   dbdata:
> ```

### Compose parancsok
* `docker compose config`: YAML ellenőrzése.
* `docker compose up -d`: Elindítja az összes definiált szolgáltatást a háttérben.
* `docker compose down`: Leállítja és törli a konténereket és a közös hálózatot.

> [!danger] Figyelem! Adatvesztés veszélye!
> A `docker compose down -v` parancs a konténerekkel együtt a **Volume-okat is törli**, ami a tartós adatok (pl. adatbázis) azonnali elvesztésével jár!

*Kiegészítés:* Nagyvállalati környezetben (több szerveren történő skálázás és orkesztráció) a Compose helyett **Kubernetes**-t használnak.

## 9. Biztonsági Jó Gyakorlatok

> [!tip] 4 Biztonsági Alapelv Dockerhez
> 1. **Megbízható image:** Csak hivatalos, validált forrásból tölts le (és figyelj a verziókövetésre).
> 2. **Minimális jogosultság:** Az alkalmazást a konténeren belül sose `root` felhasználóként futtasd, ha nem muszáj.
> 3. **Titkok kezelése:** Jelszavakat, API kulcsokat sose "égess bele" a Dockerfile-ba (használj környezeti változókat / Secret managert).
> 4. **Erőforráskorlátok:** A cgroups segítségével szabályozd a RAM és CPU limiteket, nehogy egy konténer túlterhelje az egész gazdagépet.

## 10. Kitehintés a felhőre: Azure szolgáltatások

Amikor a lokálisan kifejlesztett Docker image-ünket a felhőben (pl. Azure) szeretnénk futtatni, az architektúra a következőképp épül fel:
1. Fejlesztés (Dockerfile $\rightarrow$ Docker build).
2. **Azure Container Registry (ACR):** Ide toljuk fel (`docker push`) az image-et. (Ez csak tárol, nem futtat).
3. Futtatási platformok:
   * **Azure Container Instances (ACI):** Egyszerű, önálló konténer, gyors tesztekhez, rövid feladatokhoz.
   * **Azure Container Apps (ACA):** Menedzselt platform, biztosít automatikus skálázást, HTTPS végpontot, verzióváltást (revision).
   * **Azure Kubernetes Service (AKS):** Bonyolultabb, elosztott rendszerekhez.

## Tesztkérdések az ismétléshez

> [!faq]- Mi a legfontosabb különbség a Virtuális Gép (VM) és a Konténer izolációja között?
> A VM teljes értékű, külön "Guest" operációs rendszert futtat, így hardverszintű az izolációja. A konténer a gazdagép (Host) meglévő operációs rendszerének kernelét használja, és folyamatszinten (Namespaces és Cgroups segítségével) izolál.

> [!faq]- Mit csinál a Docker `run` parancs esetében a `-p 8080:80` paraméter?
> Ez a port mapping (portleképezés). Azt jelenti, hogy a gazdagép (host) $8080$-as portjára érkező hálózati forgalmat a Docker átirányítja a konténer belső $80$-as portjára.

> [!faq]- Mi a különbség a Dockerfile-ban a `RUN` és a `CMD` utasítások között?
> A `RUN` az image *építésekor* (build) hajtódik végre (például csomagok letöltése, telepítése). A `CMD` viszont csak akkor fut le, amikor az image-ből *elindítunk* egy konténert (futásidő), és ez határozza meg a konténer alapértelmezett folyamatát (pl. webszerver elindítása).

> [!faq]- Hogyan oldható meg, hogy a konténer törlése után se vesszenek el az adatbázis adatai?
> Tartós adattárolást (Data Persistence) kell alkalmazni, leggyakrabban Docker Volume használatával. A Volume életciklusa független a konténerétől, így a konténer törlése esetén a Volume (és a benne lévő adat) érintetlen marad.

> [!faq]- Melyik Azure szolgáltatást érdemes használni, ha egy menedzselt konténeres alkalmazást akarunk futtatni beépített HTTPS végponttal és automatikus skálázással (Kubernetes komplexitása nélkül)?
> Az Azure Container Apps (ACA) szolgáltatást. (Az ACI túl egyszerű ehhez, az AKS pedig túlságosan komplex, nyers Kubernetes megoldás).
