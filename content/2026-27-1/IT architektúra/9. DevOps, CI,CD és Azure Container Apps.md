> [!abstract] Összefoglaló
> Ez a jegyzet a modern szoftverfejlesztési életciklust mutatja be a DevOps kultúrától kezdve a CI/CD csővezetékeken (pipeline) át egészen a konténerizált alkalmazások felhőalapú üzemeltetéséig. Részletesen tárgyalja a GitHub Actions automatizációs platformot, a konténerek fogalmát, valamint a Microsoft Azure Container Apps (ACA) környezetet, amely a kódírástól az automatikus élesítésig tartó utat biztosítja.

## 1. A DevOps alapjai

A szoftverfejlesztés modern világában a kód megírása csak a folyamat kezdete. A DevOps egy olyan kultúra és gyakorlat, amely összehozza a fejlesztőket és az üzemeltetőket.

> [!cite] Mi az a DevOps?
> "A DevOps az emberek, a folyamatok és a termékek egyesítése, amely lehetővé teszi, hogy folyamatosan értéket juttassunk el a végfelhasználókhoz."
> — Donovan Brown, Microsoft

> [!definition] DevOps
> A szoftverfejlesztés (Dev) és az informatikai üzemeltetés (Ops) gyakorlatainak ötvözése, melynek célja a rendszerek fejlesztési életciklusának lerövidítése, a hibák gyorsabb javítása, és a folyamatos, magas minőségű szoftverkiadás biztosítása.

### A DevOps elősegítői (Enablers)

A DevOps sikeres implementálásához számos technológiai és módszertani eszközre van szükség:
1. **Verziókontroll (pl. Git):** Lehetővé teszi a forráskód történetének nyomon követését és a világ különböző pontjain dolgozó csapatok együttműködését.
2. **Agilis módszertanok (Kanban, Scrum):** Sprintekben való gondolkodás, gyors alkalmazkodás a változó körülményekhez, fókuszálva a rövid távú eredményekre.
3. **Infrastructure as Code (IaC):** Az infrastruktúra (szerverek, hálózatok) kódból történő, automatizált, ismételhető telepítése és lebontása.
4. **Monitorozás és felhő:** A felhő csökkenti az üzemeltetési terheket. A felelősség marad a konfigurációért és biztonságért, de a metrikák, logok azonnali visszacsatolást adnak.
5. **Mikroszolgáltatások (Microservices):** Üzleti felhasználási esetek elkülönítése kis méretű, újrafelhasználható szolgáltatásokra.

> [!done] 💡 Érthető magyarázat: Monolit vs. Mikroszolgáltatás
> Képzeld el a **monolitikus alkalmazást** egy hatalmas, egybeépített svájci bicskának, ahol ha eltörik a dugóhúzó, az egész bicskát szét kell szedni a javításhoz. A **mikroszolgáltatás** architektúra viszont olyan, mint egy jól felszerelt szerszámosláda: külön van a kalapács, a csavarhúzó és a fogó. Ha a kalapács nyele eltörik, csak azt az egy szerszámot kell kicserélned (frissítened), anélkül, hogy a többihez hozzáérnél.

### Vízesés modell vs. Agilis fejlesztés

| Szempont | Vízesés (Waterfall) modell | Agilis (Agile) megközelítés |
| :--- | :--- | :--- |
| **Folyamat** | Szigorú, egymásra épülő lépések (Specifikáció $\rightarrow$ Elemzés $\rightarrow$ Fejlesztés $\rightarrow$ Tesztelés $\rightarrow$ Szállítás). | Iteratív, folyamatosan adaptív tervezés és folyamatos fejlesztés. |
| **Követelmények** | Nehéz pontosan specifikálni, változásuk drága. | A változásokra rugalmasan reagál. |
| **Tesztelés és fókusz** | Csak a fejlesztési fázis legvégén történik a teszt. | Minden iteráció (sprint) végén működő kódot tesztelnek. Rövid távú eredményekre fókuszál. |

## 2. CI/CD: A szoftverkiadás csővezetéke (Pipeline)

A pipeline (csővezeték) teszi lehetővé a változtatások folyamatos, megbízható és automatizált áramlását a forráskódtól az ügyfélig egy automatizált szoftvergyártó vonalon keresztül.

> [!done] 💡 Érthető magyarázat: A CI/CD csővezeték
> A CI/CD pipeline leginkább egy modern autógyár szerelőszalagjához hasonlít. Amint a mérnök (fejlesztő) megtervez egy új alkatrészt (commit), az felkerül a szalagra. A robotok azonnal megvizsgálják, hogy beépíthető-e (CI - automata tesztek). Ha minden tökéletes, a szalag továbbviszi az autót, és egy minőségellenőr jóváhagyásával (Delivery) vagy akár teljesen automatikusan, emberi érintés nélkül (Deployment) legurul a gyárból egyenesen a kereskedésbe.

### A fejlesztés automatizáltságának 3 szintje

| Szint | Megnevezés | Jellemzők és Eredmény |
| :---: | :--- | :--- |
| **1.** | **Continuous Integration (CI)** | Minden kód-commit után elindul egy **automatikus build és tesztelés**. Védi a `main` ágat. *Eredmény:* Ellenőrzött, tiszta kód. |
| **2.** | **Continuous Delivery (CD)** | Az integrált kód automatikusan egy kiadható állapottá (pl. Docker image) alakul. A **tényleges élesítéshez (deploy) emberi jóváhagyás** szükséges. |
| **3.** | **Continuous Deployment (CD)** | Ha a kód átmegy minden teszten, **automatikusan és azonnal kikerül az éles környezetbe** emberi beavatkozás nélkül. |

### A Continuous Integration 4 pillére
1. **Version control system:** Verziókezelő, ami a forráskód időbeli változásait kezeli.
2. **Package management system:** Csomagkezelő a szoftvercsomagok telepítéséhez, eltávolításához, menedzseléséhez.
3. **Continuous integration system:** A rendszer, ami egyesíti a fejlesztők munkáit, akár naponta többször is.
4. **Automated build process:** Automatizált folyamat, ami létrehozza a szoftver összeállítást (build): tartalmazza a fordítást, csomagolást és a tesztek futtatását.

> [!warning] A CI (Folyamatos Integráció) előnyei
> - A gyors visszajelzések javítják a kód minőségét.
> - Minden változás automatikus tesztelést indít el.
> - A hibák korai felderítése csökkenti a kockázatokat és a javítási költségeket.
> - A hosszú, nehéz összevonások (merge) csökkennek, tisztán tartja a fő ágat.
> - Hatékonyabban kezeli a technikai adósságot, növeli a kódbázisba vetett bizalmat az élesítés előtt.

## 3. GitHub Actions (Az automatizáció motorja)

A gyakorlatban a GitHub Actions-t használjuk a CI/CD folyamatok felépítésére (például a folyamat: build $\rightarrow$ Docker Hub push $\rightarrow$ Azure Container Apps update).

> [!definition] Runner
> A Runner nem egy pipeline-fázis, hanem az a dedikált végrehajtási környezet (pl. egy GitHub által hosztolt Ubuntu Linux gép `ubuntu-latest`), amelyen a feladatok (Job-ok) lépései ténylegesen lefutnak.

**A Workflow (Munkafolyamat) felépítése:**
1. **Trigger:** Az esemény, ami kiváltja a folyamatot (pl. `push` vagy `pull_request` vagy `workflow_dispatch`).
2. **Job:** A feladat, ami egy dedikált **Runner**-en fut. Egy workflow több job-ból is állhat. Ha egy lépés sikertelen, a deployment nem folytatódik.
3. **Steps:** A job-on belüli konkrét, egymás után végrehajtandó lépések (pl. checkout, build, push, deploy).

> [!example] Minimális GitHub Actions Workflow
```yaml
name: Container CI
on: [push] # Trigger: Push a GitHub-repositoryba
jobs:
  build: # Job neve
    runs-on: ubuntu-latest # Runner környezet
    steps:
      - uses: actions/checkout@v4 # 1. Step (kód letöltése)
      - name: Build image # 2. Step
        run: docker build -t demo-web:ci .
```

## 4. Konténerizáció és Docker

A konténer egy szabványos "szoftveregység", amely mindent tartalmaz, ami egy alkalmazás futtatásához szükséges (kód, runtime, rendszereszközök, könyvtárak). A Docker Platform Linuxon és Windowson egyaránt elérhető.

> [!danger] Miért fontos a konténer a DevOps-ban?
> A legfőbb érv: **Hordozhatóság és Konzisztencia.** Megszünteti a hírhedt *"de az én gépemen még működött!"* problémát. Ahol a Docker fut, ott a konténerek is futnak, így a fejlesztők garantáltan azonos kóddal és környezettel dolgoznak.

### Konténer vs. Virtuális Gép (VM)

> [!done] 💡 Érthető magyarázat
> Képzeld el a **Virtuális Gépeket (VM)** úgy, mint különálló, kerítéssel körbevett családi házakat. Mindegyiknek saját alapozása, saját víz- és villanyhálózata (saját Vendég Operációs Rendszere / Guest OS) van. Nagyon elszigeteltek, de sok erőforrást pazarolnak.
> A **Konténerek** ezzel szemben egy nagy társasház lakásai. A lakók (alkalmazások) el vannak szigetelve egymástól (saját ajtó/zár), de közösen használják a ház alapvető infrastruktúráját (Host OS Kernel). Így sokkal könnyebbek (kisebb súlyúak), gyorsabban indíthatók (percek helyett másodpercek) és hatékonyabb erőforrás-használatot biztosítanak.

### Container Registry-k (Képtárolók)
Miután a kód lefordul egy kész image-be, azt tárolni kell valahol.

1. **Docker Hub:** Általános, nyilvános (vagy privát) image-registry. 
2. **GitHub Container Registry (GHCR):** A GitHub-folyamatokhoz illeszkedő registry.
3. **Azure Container Registry (ACR):** Azure-ban üzemeltetett, OCI-kompatibilis privát registry. Támogatja az ACR Tasks-t (amely egyszerűsíti a képek készítését/telepítését). Szolgáltatási szintek: Basic, Standard, Premium.

> [!tip] Költségtakarékossági tanács
> Az Azure Container Registry (ACR) használata díjköteles lehet akkor is, ha kevés image-et tárolunk. Az egyetemi gyakorlatokon a legköltséghatékonyabb útvonal egy publikus **Docker Hub** image használata.

## 5. Azure Konténer Szolgáltatások

A Microsoft Azure többféle platformot kínál konténerek futtatására, az egyszerűtől a rendkívül komplexig.

| Szolgáltatás neve | Jellemzők |
| :--- | :--- |
| **Azure Container Instances (ACI)** | A leggyorsabb módja egy konténer elindításának az Azure-ban virtuális gép kiépítése nélkül. Egyszerű konténerfuttatás, gyors feladatokhoz. (PaaS szolgáltatás). |
| **Azure Container Apps (ACA)** | Menedzselt, szerver nélküli alkalmazás futtatás (mikroszolgáltatásokhoz). Támogatja a dinamikus skálázást (KEDA alapján), revíziókat, ingress-t és Dapr integrációt. |
| **Azure Kubernetes Service (AKS)** | A konténerek "vezénylésének" (orchestration) de facto szabványa. Nagyobb üzemeltetési kontrollt ad, komplex rendszerekhez. |
| **Azure App Service** | Felügyelt szolgáltatás webalkalmazásokhoz (Windows és Linux alapú egyaránt), támogatott konténeres telepítéssel. |

## 6. Fókuszban: Azure Container Apps (ACA)

Az Azure Container Apps-ban a tárolók a felülvizsgálati pillanatképeken (revision snapshots) belül *pod*-okban vannak csoportosítva. Egy alkalmazáson belül több tároló is lehet.

### Erőforrás-hierarchia

> [!definition] Azure Container Apps hierarchia
> 1. **Environment (Környezet):** Közös hálózati és üzemeltetési biztonsági határ a tárolóalkalmazások csoportja körül.
> 2. **Container App (Alkalmazás):** Maga az alkalmazás és annak specifikus konfigurációja.
> 3. **Revision (Revízió):** Az image, vagy a konfiguráció egy adott *verziója (pillanatképe)*. A forgalom irányítható a különböző aktív revíziók között (single vagy multiple revision mode).
> 4. **Replica (Példány):** Egy adott revízió *konkrétan futó példánya*. A skálázási szabályok (terhelés) alapján változhat a számuk.

*   **Ingress:** A hálózati bejárat (External HTTPS URL). A célportra (target port, pl. 80 az Nginx esetén) érkezik a forgalom, és ez juttatja el azt a konténerhez.

### Biztonság és Hitelesítés (Secrets & OIDC)

Az ACA CI/CD pipeline két külön jogosultsági utat használ:
1. **GitHub Actions $\rightarrow$ Azure telepítés (Deployment):** Ehhez **OIDC (OpenID Connect)** tokenes, úgynevezett federált hitelesítés kell (Azure Entra ID, Azure RBAC jogosultság). Ennek segítségével a token ellenőrzése után a GitHub frissítheti a Container App konfigurációját. Így **nem kell tartós Azure-jelszót tárolni** a GitHub Secrets-ben!
2. **Container App $\rightarrow$ Registry image-letöltés:** Ahhoz, hogy az ACA le tudja tölteni (pull) az image-et egy privát registryből (pl. ACR), külön hitelesítő adatok kellenek. Publikus Docker Hub esetében ez sima nyilvános pull, privát ACR-nél akár *Managed Identity* is használható.

> [!danger] Kiberbiztonsági aranyszabály
> **Titkokat (secrets, jelszavakat, hozzáférési kulcsokat) soha ne írjunk bele a Dockerfile-ba vagy a nyílt Git-repositoryba!** Ezeket az alkalmazás szintjén, az Azure platformon kell kezelni, és a revíziók csak hivatkoznak rájuk. (Fontos: egy secret puszta módosítása nem feltétlenül indít el rögtön egy új revíziót).

## 7. Vizsgafelkészítő Tesztkérdések

> [!faq]- Milyen különbségek vannak a VM (Virtuális gép) és a Konténer között operációs rendszer és elszigeteltség szempontjából?
> A VM-ek hardver szintű virtualizációt használnak, ami azt jelenti, hogy minden egyes virtuális gép egy teljesen különálló, saját operációs rendszert (Guest OS) futtat egy Hypervisor felett, ami erőforrás-igényessé és lassabban indulóvá teszi őket. A konténerek viszont a gazdagép (Host) operációs rendszerének magját (kernelét) osztják meg, csak a futtatáshoz elengedhetetlen fájlokat és könyvtárakat tartalmazzák. Így sokkal kisebbek, elszigeteltek, és másodpercek alatt elindulnak.

> [!faq]- Mi a különbség a Continuous Delivery és a Continuous Deployment között?
> Mindkettőnél a kód automatikusan lefordul, tesztelésre kerül, és létrejön a telepítésre kész csomag (pl. Docker image). A különbség az utolsó lépésben van: a Continuous Delivery esetén a rendszer megáll, és az éles (production) környezetbe történő telepítéshez (deploy) emberi engedélyezés (pl. gombnyomás) szükséges. A Continuous Deployment esetén viszont nincs emberi beavatkozás: ha a kód átmegy a teszteken, az azonnal, teljesen automatikusan kikerül az éles környezetbe.

> [!faq]- Mit jelent az OIDC (OpenID Connect) token szerepe a GitHub Actions és az Azure közötti kommunikációban?
> Az OIDC teszi lehetővé, hogy a GitHub Actions biztonságosan bejelentkezzen és módosításokat (deployment) végezzen az Azure felhőben anélkül, hogy hosszú lejáratú, statikus jelszavakat vagy hitelesítő kulcsokat kellene menteni a GitHub Secrets-be. A folyamat során egy rövid életű OIDC tokent cserélnek, amelyet az Azure Entra ID ellenőriz, biztosítva a legkisebb szükséges jogosultság elvét.

> [!faq]- Az Azure Container Apps hierarchiájában mi a Revision (Revízió) és a Replica (Példány) definíciója?
> A **Revision** a tárolóalkalmazás image-ének vagy konfigurációjának egy specifikus, adott pillanatképe (verziója). Ha módosítjuk a beállításokat vagy az image-et, egy új revízió jön létre. Ezzel szemben a **Replica** egy adott revízió konkrétan futó konténer-példánya (pod). Amikor a terhelés megnő, a rendszer skálázási szabályok alapján az aktuális revízióból több replicát indít el, hogy kiszolgálja a forgalmat.

> [!faq]- Egy GitHub Actions Workflow-n belül mi a pontos különbség a Trigger és a Runner között?
> A **Trigger** (kiváltó ok) egy specifikus esemény, amely elindítja magát az automatizált folyamatot, például egy "push" kód feltöltés a "main" ágra. A **Runner** ezzel szemben maga a végrehajtó virtuális számítógép (környezet, pl. `ubuntu-latest`), ahol a Workflow feladatai (Job-ok) és szkriptjei (Steps) ténylegesen lefutnak. Nem a pipeline része, hanem a futtató infrastruktúra.
