> [!abstract] Rövid összefoglaló
> Ez a jegyzet a verziókezelő rendszerek alapjaival, különösen a Git elosztott architektúrájával és gyakorlati működésével foglalkozik. Részletesen tárgyalja a helyi és távoli repozitóriumok kezelését, a párhuzamos fejlesztés eszközeit (branch, merge), valamint kitér a modern CI/CD munkafolyamatokra és a felhős (GitHub, Azure DevOps) integrációkra is.

## 1. Miért van szükség verziókezelésre?

Egy projekt során (legyen az szoftverfejlesztés vagy dokumentumírás) az egyik leggyakoribb probléma a **fájlok verzióinak követése**. Ha a verziókat csak a fájlnevekben tároljuk (pl. `koltsegvetes.xlsx`, `koltsegvetes_vegleges.xlsx`, `koltsegvetes_vegleges2_jo.xlsx`), az alábbi problémákba ütközünk:
*   Nehéz megállapítani, **ki** és **mit** módosított.
*   A **párhuzamos módosítások** (amikor többen dolgoznak ugyanazon) felülírhatják egymást és elveszhetnek.
*   Nagyon nehéz **visszaállítani** egy korábbi, még működő állapotot.
*   Bizonytalan, hogy melyik az aktuális, jóváhagyott változat.

> [!example] Különböző megközelítések a közös munkára
> **1. Közös irodai dokumentumok (Microsoft 365):**
> Ha *Anna* (pénzügy), *Béla* (értékesítés) és *Csilla* (vezető) ugyanazt az Excelt szerkesztik OneDrive-on, a felhőalapú közös szerkesztés azonnal szinkronizál. Bár van verzióelőzmény, ez **nem azonos** a Git modelljével, mert a változások azonnal a központi fájlba kerülnek.
> 
> **2. Közös szoftverfejlesztés (Git, Azure DevOps):**
> Ha *Anna* egy új képernyőt fejleszt, *Béla* hibát javít, *Csilla* pedig menüt alakít át ugyanabban az alkalmazásban, szükség van **párhuzamos, elszigetelt fejlesztésre**, konfliktuskezelésre és a kód egyesítés előtti ellenőrzésére.

> [!definition] Verziókezelő rendszer (VCS)
> Olyan szoftveres rendszer, amely rögzíti a fájlok vagy fájlhalmazok időbeli változásait, lehetővé téve a változástörténet követését, a korábbi állapotok visszaállítását, és a többfelhasználós, párhuzamos együttműködést.

### Mit nyújt egy profi verziókezelő?
1.  **Változástörténet:** Ki, mikor, mit változtatott?
2.  **Visszaállítás:** Korábbi működő állapot azonnali visszakeresése.
3.  **Párhuzamos munka:** Egymástól független módosítások lehetősége (branching).
4.  **Egyesítés és ellenőrzés:** Változások összevezetése és felülvizsgálata (merging, code review).

## 2. Verziókezelési modellek

A repozitóriumok (adattárak) és a változástörténet tárolása alapján három fő modellt különböztetünk meg:

| Modell | Jellemzők | Példák (Szoftverek) |
| :--- | :--- | :--- |
| **Lokális** | A változatok egyetlen számítógépen találhatók. Ma már főként csak történeti jelentősége van. | RCS |
| **Centralizált (CVCS)** | Egy **központi szerverre** épül. A fejlesztők csak a munkapéldányt (aktuális állapotot) töltik le. | SVN, TFVC, Perforce Helix Core |
| **Elosztott (DVCS)** | Minden fejlesztő gépén ott van a **teljes klón**, a saját helyi verziótörténettel. Hálózat nélkül is működik. | **Git**, Mercurial |

> [!done] 💡 Érthető magyarázat a modellekhez
> **Centralizált (SVN):** Képzelj el egy központi könyvtárat. Csak kikölcsönözni tudsz egy könyvet (fájlt), elolvasod, majd visszaviszed. Ha nincs interneted, nem férsz hozzá a könyvtár archívumához.
> **Elosztott (Git):** Képzeld el, hogy a varázspálcáddal az *egész* könyvtárat, annak összes archívumával együtt lemásolod a saját hátizsákodba. A buszon (offline) is bármikor visszanézheted az 5 évvel ezelőtti köteteket, és írhatsz új oldalakat. Később, ha van neted, csak szinkronizálod a hátizsákod tartalmát a főkölcsönzővel.

## 3. Git vs. GitHub vs. Azure DevOps

> [!warning] Gyakori tévhit
> A Git és a GitHub **nem** ugyanaz! A Git maga a technológia, a GitHub pedig egy erre épülő szolgáltatás.

1.  **Git (Verziókezelő eszköz):** Linus Torvalds által 2005-ben létrehozott *elosztott verziókezelő rendszer*. A gépeden fut, hálózat nélkül is használható (commit, branch, merge).
2.  **GitHub (Platform):** Egy felhőalapú szolgáltatás (Git-hosting), amely távoli repozitóriumokat tárol. Támogatja a csoportmunkát: Pull request, Code review, GitHub Actions (CI/CD).
3.  **Azure DevOps (Platform):** A Microsoft vállalati megoldása. Képes Git és TFVC (Team Foundation Version Control) alapú repozitóriumokat is kezelni (*Azure Repos*), és beépített CI/CD eszköze van (*Azure Pipelines*).

## 4. A Git 4 területe (Hogyan utazik a fájl?)

Amikor egy fájllal dolgozunk a Gitben, az négy különböző logikai "zónán" halad keresztül, mire eljut a felhőbe.

1.  **Working directory (Munkakönyvtár):** Itt találhatók a projekt tényleges, szerkeszthető fájljai. Te itt dolgozol.
2.  **Staging area (Előkészítési terület):** Ide kerülnek azok a változások, amiket a *következő* commitba bele akarsz tenni. (A `git add` paranccsal).
3.  **Local repository (Helyi repozitórium):** A te gépeden lévő helyi verziótörténet. A `.git` rejtett mappában tárolódik. (A `git commit` paranccsal jön létre az új verzió).
4.  **Remote repository (Távoli repozitórium):** A felhőben (pl. GitHub) lévő szerver. (A `git push` paranccsal kerülnek fel ide a commitjaid).

> [!done] 💡 Érthető magyarázat a Staging area-ra
> Képzeld el, hogy utazásra pakolsz. 
> *   A **Working Directory** a szobád, ahol minden ruhád szét van szórva.
> *   A **Staging Area** az ágyad, amire szépen kikészíted azokat a ruhákat, amiket a bőröndbe *szánsz*. (Nem mindent viszel el a szobából!)
> *   A **Commit** az, amikor lezárod (becipzározod) a bőröndöt, és ráteszel egy címkét, hogy "Nyári utazás 2026".
> *   A **Push** pedig az, amikor a bőröndöt felrakod a repülőre.

> [!danger] Figyelem!
> A `git commit` mindig **helyben** történik! Egyedül a `git push` az a parancs, ami kommunikál az internettel (a távoli szerverrel).

## 5. Alapvető Git parancsok és munkafolyamat (Linux/Debian)

### Inicializálás és beállítás
Mielőtt elkezdenénk, a Gitnek tudnia kell, kik vagyunk (ez lesz a commitokon).
```bash
# Globális beállítások
git config --global user.name "Vezetéknév Keresztnév"
git config --global user.email "nev@example.com"
```
*(Ezek az adatok nem egyeznek meg a GitHub bejelentkezési adatokkal, csak szerzői metainformációk.)*

Új repozitórium létrehozása a helyi gépen:
```bash
mkdir linux-monitor
cd linux-monitor
git init -b main  # Inicializálja a repót, a fő ág neve 'main' lesz
```
*Ilyenkor létrejön egy rejtett `.git` könyvtár, amit soha ne szerkesszünk kézzel!*

### Fájlok követése: Tracked vs. Untracked
*   **Untracked (nem követett):** Új fájl, amit a Git még nem ismer.
*   **Tracked (követett):** Olyan fájl, amit a Git már figyel.

> [!tip] A legfontosabb parancs
> A `git status` a legjobb barátod! Bármit csinálsz, ez a parancs megmutatja, milyen állapotban vannak a fájljaid (melyik van a stagingben, mi módosult stb.). Használd folyamatosan!

### Az első commit folyamata
```bash
# 1. Fájl létrehozása
printf '#!/bin/bash\n' > monitor.sh
printf 'hostname\n' >> monitor.sh
chmod +x monitor.sh

# 2. Hozzáadás a Staging Area-hoz (előkészítés)
git add monitor.sh

# 3. Rögzítés a Helyi repozitóriumban (Commit)
git commit -m "Első monitor szkript"
```

> [!definition] Commit
> A projekt egy adott időpillanatban rögzített, visszakereshető állapota (pillanatképe). Nem egy egyszerű mentés; minden commit kap egy egyedi azonosítót (hash), időbélyeget és szerzői adatokat.

### Változtatások megtekintése
*   `git diff`: Megmutatja a munkakönyvtár és a staging area közötti eltéréseket (mi változott a fájlban).
*   `git log`: Megjeleníti a commit előzményeket (történetet). Rövidítve: `git log --oneline`.
*   `git show HEAD`: Megmutatja a legutóbbi commit részleteit. A **HEAD** egy mutató (pointer), ami az aktuálisan kijelölt commitra mutat.

## 6. Párhuzamos munka: Branch és Merge

Amikor egy új funkciót fejlesztünk (pl. egy új menüpont), nem akarjuk rögtön az éles kódot (`main` ág) piszkálni, nehogy elrontsuk. Erre valók a branchek.

*   `git branch`: Kilistázza a meglévő ágakat.
*   `git switch -c feature/uptime`: Létrehoz egy új ágat `feature/uptime` néven, és azonnal át is vált rá.

> [!cite] Branching filozófia
> "A feature ágban új funkció fejleszthető a main ág közvetlen módosítása nélkül."

Miután elkészültünk a fejlesztéssel az új ágon, a **Merge** (összeolvasztás) művelettel tudjuk visszavinni a változásokat a `main` ágba.
```bash
# Visszaváltunk a fő ágra
git switch main
# Beolvasztjuk a feature ágat a main-be
git merge feature/uptime
```

### Merge Conflict (Ütközés)
Ha ketten is módosították **ugyanannak a fájlnak ugyanazt a sorát** (pl. egyik a `main` ágon "Disk: 70%"-re, másik a `feature/disk` ágon "Disk: 80%"-ra írta át), a Git nem tudja automatikusan egyesíteni (fast-forward merge). Ekkor **konfliktus** alakul ki.

A fájlban ilyenkor speciális jelölések jelennek meg:
```bash
<<<<<<< HEAD
echo "Disk: 70%"
=======
echo "Disk: 80%"
>>>>>>> feature/disk
```
**A feloldás menete:** Kézzel ki kell törölni a jelölőket, meghagyni a helyes (kívánt) kódot, majd a fájlt újra `git add` és `git commit` paranccsal kell rögzíteni.

## 7. GitHub és a Távoli repozitórium (Remote)

Ahhoz, hogy a kódunk megosztható legyen, fel kell töltenünk egy távoli szerverre (pl. GitHub, Azure Repos).

### Helyi repó összekötése a GitHubbal
```bash
# Hozzáadjuk a távoli repó URL-jét 'origin' néven
git remote add origin https://github.com/FELHASZNALO/linux-monitor.git

# Feltöltjük a 'main' ágat (a -u beállítja a jövőbeli alapértelmezett kapcsolatot)
git push -u origin main
```

> [!warning] Hitelesítés (Authentication)
> GitHub esetén a HTTPS kapcsolathoz **nem használható a fiók jelszava** a terminálban! Helyette javasolt a GitHub CLI (`gh auth login`) használata, vagy SSH-kulcs, esetleg személyes hozzáférési token (PAT - Personal Access Token) alkalmazása. Soha ne tároljunk titkos kulcsokat a repozitórium fájljaiban!

### Adatszinkronizációs parancsok (Fetch vs. Pull)
*   `git fetch`: Letölti a távoli repón történt változásokat (a kollégák commitjait) a gépedre, de **nem módosítja** a te munkakönyvtáradat. (Jó ellenőrzésre).
*   `git pull`: Letöltés ÉS azonnali integrálás. (Gyakorlatilag egy `fetch` + `merge` egyben).
*   `git push`: A te helyi commitjaidat tölti fel a távoli szerverre.

### Közös munkafolyamat a weben (Pull Request)
A GitHubon a kód beolvasztása a fő ágba gyakran **Pull Request (PR)** formájában történik. 
1. Branch pusholása.
2. PR nyitása a weben.
3. Code review (csapattársak átnézik a kódot).
4. Jóváhagyás után weben keresztül történik a Merge.

*(Megjegyzés: A pull request nem hivatalos Git-parancs, hanem a GitHub/Azure felületek által nyújtott kollaborációs eszköz).*

## 8. CI/CD és GitOps (Fejlett architektúra)

A modern IT üzemeltetésben a Git már nem csak fájlok tárolására, hanem automatizálásra is szolgál.

*   **CI (Continuous Integration - Folyamatos integráció):** Amikor egy `git push` történik, a felhős szerver (pl. GitHub Actions) automatikusan lefordítja (Build) a kódot és lefutnak az automatikus tesztek.
*   **CD (Continuous Deployment - Folyamatos telepítés):** Ha a tesztek sikeresek, a kód automatikusan kikerül az éles környezetbe (pl. Azure App Service).

> [!definition] Infrastructure as Code (IaC)
> Az az elv, amikor a hardveres/felhős infrastruktúrát (virtuális gépek, hálózatok) is programkódként (pl. Bicep, Terraform) írjuk le, és ezt a kódot is Gitben verziókezeljük. 

**GitOps szemlélet:**
A "kívánt állapotot" a Gitben tároljuk. Egy automatizmus folyamatosan figyeli ezt, és ha eltérést tapasztal a valódi infrastruktúra (tényleges állapot) és a Git kód (elvárás) között, akkor a Gites állapotot kényszeríti ki.

## 9. Vizsgafelkészítő tesztkérdések

> [!faq]- Mi a különbség a `git commit` és a `git push` között?
> A `git commit` egy új pillanatképet (verziót) hoz létre és rögzít a te **helyi géped** repozitóriumában (`.git` mappa). Hálózat nélkül is működik. Ezzel szemben a `git push` a már rögzített helyi commitokat küldi el az interneten keresztül egy **távoli szerverre** (pl. GitHubra), hogy mások is láthassák azokat.

> [!faq]- Mit csinál a `git status` parancs, és miért fontos?
> A `git status` megmutatja a munkakönyvtár és a staging area (előkészítési terület) aktuális állapotát. Kilistázza a módosított, a követetlen (untracked), és a következő commitba bekészített (staged) fájlokat. Ez a legfontosabb ellenőrző parancs, amivel mindig tisztában lehetünk azzal, hogy hol tartunk.

> [!faq]- Hogyan tudjuk kiküszöbölni, hogy a `main` ágat közvetlenül módosítsuk fejlesztés közben?
> Az úgynevezett **branching** (ágaztatás) technikával. Létrehozunk egy új ágat (pl. `git switch -c feature/uj-funkcio`), és az új fejlesztéseket ezen az elszigetelt ágon végezzük. Amikor a fejlesztés kész és tesztelt, a módosításokat a `git merge` paranccsal olvasszuk be a `main` ágba.

> [!faq]- Mi történik, ha egy 'Merge conflict' (ütközés) lép fel, és hogyan lehet megoldani?
> Ütközés akkor jön létre, ha két különböző ágon (vagy egy kollégával párhuzamosan) **ugyanannak a fájlnak pontosan ugyanazt a sorát** módosítottuk, és a Git nem tudja eldönteni, melyik a helyes. A fájlban speciális `<<<<<<<`, `=======`, `>>>>>>>` jelölők jelennek meg. A megoldáshoz kézzel meg kell nyitni a fájlt, kiválasztani a helyes kódrészletet, törölni a Git jelölőit, majd a fájlt újra elő kell készíteni (`git add`) és commitolni (`git commit`).

> [!faq]- Mi az az Infrastructure as Code (IaC) és hogyan kapcsolódik a Githez?
> Az IaC (Infrastruktúra kódként) azt jelenti, hogy a szervereket, hálózatokat és felhős erőforrásokat (pl. Azure Bicep vagy Terraform segítségével) deklaratív programkódként írjuk le, ahelyett, hogy kézzel kattintgatnánk össze őket egy felületen. Mivel ez szöveges kód, tökéletesen tárolható és verziókezelhető a **Gitben**, így az infrastruktúra változásai is pontosan követhetők, auditálhatók és visszaállíthatók lesznek.
